# Explanation Quality Check (Phase 6)

All data is simulated, so these results show that the explanation step works on data generated by this project. They do not show how it would perform on real fraud.

## 1. How explanations are made

1. Take the account's five features, scaled with the saved Phase 4 scaler.
2. Multiply each scaled value by +1 or -1 so that bigger always means more suspicious (high is suspicious for trades per day, spike ratio and linked accounts; low is suspicious for account age and timing regularity).
3. Pick the top two features, but only keep a feature if its score is at least `MIN_SCORE = 1.5` standard deviations.
4. Fill a fixed sentence template for each kept feature, using the account's real (unscaled) values.
5. If no feature reaches 1.5, return a fixed fallback sentence: "No feature looks clearly suspicious on its own; review the account's raw values."

The text comes only from templates, so it cannot invent facts. The same code (`explain_raw` in `src/explain.py`) is used for the review table and, later, for the API.

## 2. How quality was checked

### 2.1 Hand spot-check (Step 7)
I checked 12 random flagged accounts (6 per method) against their real feature values. In all 12 samples from the final check, every number in the sentence matched the real value. The wording problems found are listed in section 4.

### 2.2 Check against the hidden labels (Step 8)
Labels were used only for this check, never to build explanations.

A flagged account counts as a **hit** if its explanation mentions at least one feature that its abuse type manipulates:

| Abuse type | Features it manipulates |
|---|---|
| trial_abuse | account age, trades per day, spike ratio |
| multi_account | linked accounts |
| bot | timing regularity |

Only flagged accounts that really are anomalies are counted (single run, top 3% budget, 99 anomalies in total).

| Method | Real anomalies flagged | Hits | Hit rate |
|---|---|---|---|
| Z-score | 84 | 84 | 100% |
| Isolation Forest | 66 | 66 | 100% |

By abuse type (flagged real anomalies, all hits): z-score caught 33 trial abuse, 33 multi-account, 18 bot; Isolation Forest caught 33, 28 and 5. By difficulty: z-score 51 obvious and 33 subtle; Isolation Forest 38 obvious and 28 subtle.

These counts agree with the Phase 5 results in `data/model_comparison.csv` (5-seed mean recall 0.836 for z-score and 0.667 for Isolation Forest; bot recall is the weak spot for both).

**What the 100% does and does not mean:** it shows the sentences point at features that really were manipulated. It does not show the explanations are insightful. The explanations use the same features the abuse was generated from, so a high hit rate is partly expected by design. It was measured on a single run, not averaged over seeds.

## 3. Limitations found

1. **Trial abusers are described by volume, not newness.** Only 3 of 33 trial-abuse explanations mention account age (for each method; 6 of 66 combined). Age is scaled linearly, so even a brand-new account reaches only about 1.7 standard deviations, while the log-scaled volume features reach 5 to 12 and take the two slots. The sentences are true but leave out the defining trait.
2. **The explanation is not always the reason for the flag.** The z-score method uses absolute z-scores, so 3 of 93 flags were triggered by a harmless direction (very irregular timing). The explanation for those describes other features, or the fallback sentence.
3. **Zero baselines are never described as a spike.** `build_features()` sets the spike ratio to 1.0 when the baseline is 0 ("normal pace"). The explanation never says "infinite pace", but it also cannot flag a jump from a zero baseline.
4. **Explanations say which features looked unusual, not why the abuse happened.**
5. **The fallback appears for 4 of 186 review rows** (4 of the flagged rows had no feature above the 1.5 cutoff).

## 4. Problems we faced and how they were fixed

| # | Problem | Cause | Fix |
|---|---|---|---|
| 1 | `KeyError: 'spike_ratio'` when looking up raw values | `features.csv` has no spike ratio column (it is built in Phase 4) | Build raw values with the real `build_features()` |
| 2 | Raw and scaled values easy to mix up | Sentences need real values, ranking needs scaled values | Two tables: `feats` for sentences, `scaled` for ranking |
| 3 | Notebook code differed from the real pipeline | Notebook divided by the baseline (could give infinity); `build_features()` turns a zero baseline into 1.0 | Notebook now uses `build_features()` and `prepare_for_model()` from `src/` |
| 4 | Lookups by row number failed after switching tables | Real tables are indexed by `account_id` | Use `.loc["ACC00526"]` style lookups |
| 5 | Misleading second reasons ("only 264 days old", "1.2x its usual pace") | Always took the top two even when the second was normal | Added a minimum score for a feature to be mentioned, with a fallback |
| 6 | Bad grammar and odd text ("1 days", "only 0 days", "1 other accounts") | Fixed templates | `make_piece` handles singular/plural and says "created today" |
| 7 | Fallback text claimed "the combination looks unusual" when one harmless feature caused the flag | Wording was not always true | Changed to a sentence that is always true |
| 8 | Review table and CSV looked out of date after the fixes | `explain_account` was defined three times, and the table was built with the old version; a check also searched for the old fallback text | Rebuilt the notebook with one copy of each function, in order, and ran it top to bottom |
| 9 | A comparison cell reset `MIN_SCORE` to 1.0 at its end | Leftover restore line | Set it to 1.5 or removed the cell before the final run |
| 10 | Wrong cutoff left "only 173 days old"-style sentences | `MIN_SCORE = 1.0` was too low for age | Tested 1.0 vs 1.5 on real numbers, chose 1.5 (below) |
| 11 | Harmless-direction z-score flags (see limitation 2) | Z-score uses absolute values | Measured (3 of 93), kept the Phase 5 method unchanged, documented |
| 12 | Trial abuse explanations rarely mention age (see limitation 1) | Age is scaled linearly, volume features are log-scaled | Documented, not changed |
| 13 | Tests need to be run from the repo root | Imports use `src.` paths | Run `python -m pytest tests/test_explain.py` |

### The `MIN_SCORE` decision (1.0 vs 1.5)

| | 1.0 | 1.5 |
|---|---|---|
| Fallback explanations | 3 | 4 |
| "only 1xx/2xx days" sentences | 4 | 0 |
| Hits (z-score / Isolation Forest) | 84 of 84 / 66 of 66 | 84 of 84 / 66 of 66 |
| Trial abuse explanations mentioning age | 6 of 66 | 6 of 66 |

1.5 removes the misleading age wording at the cost of one more fallback and loses no hits.

## 5. Tests

`tests/test_explain.py` has 8 tests, all passing: every account and every saved review row has a non-empty explanation; quoted numbers match the input; a zero baseline gives no "inf" or "nan"; singular and plural grammar; a normal account gets the fallback; a missing column is rejected; the same input gives the same output.
