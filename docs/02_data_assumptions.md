# Data Assumptions

## 1. The data is simulated

Every account in this project is generated by code (`src/generate_data.py`). **No real trading data was used, and no real fraud was found.** Real fraud data is not public, so the generator creates accounts where I secretly know which ones are abusive. That lets me measure how well each detector works.

The consequence: **results show that the pipeline works on data built this way. They do not show how it would perform on real fraud.** A detector that does well here has found patterns I put in; real abusers may behave differently.

## 2. Reproducibility

- All settings live in `config.yaml` (random seed, account counts, fraction of subtle anomalies).
- One seeded random generator (`numpy.random.default_rng(seed)`) is used for everything, and the final shuffle uses the same seed. The same config always produces the same dataset.
- The test suite (`tests/test_data.py`) checks that two runs with the same seed are identical.

## 3. Dataset size

| Group | Accounts |
|---|---|
| Normal | 3,000 |
| Trial abuse | 33 (17 obvious, 16 subtle) |
| Multi-account | 33 (17 obvious, 16 subtle) |
| Bot | 33 (17 obvious, 16 subtle) |
| **Total** | **3,099** (about 3.2% abusive) |

33 x 0.5 is 16.5, so the split rounds to 16 subtle and 17 obvious per type.

## 4. Files and label separation

- `data/features.csv`: the columns the models see (`account_id`, `account_age_days`, `trades_per_day`, `baseline_trades_per_day`, `linked_account_count`, `timing_regularity`).
- `data/labels.csv`: the hidden truth (`account_id`, `is_anomaly`, `anomaly_type`, `difficulty`). Used only to evaluate detectors and to colour charts, never to build features or train models.
- Account IDs are assigned **after** shuffling, so an ID reveals nothing about whether an account is abusive.

Keeping labels in a separate file makes label leakage structurally hard: feature code never needs to open the labels file. A unit test confirms no label column appears in the features file.

## 5. How normal accounts are created

| Column | How it is generated | Reasoning |
|---|---|---|
| `account_age_days` | Uniform integer, 1 to 900 | Accounts of all ages exist |
| `baseline_trades_per_day` | Lognormal, median 8, sigma 0.8 | Most accounts trade a moderate amount; a few are heavy traders |
| `trades_per_day` | Baseline x lognormal wobble (sigma 0.2, about 20%) | Normal accounts stay close to their own usual pace |
| `linked_account_count` | 0 (75%), 1 (22%), 2 (3%) | Most accounts share no device or IP |
| `timing_regularity` | Normal(mean 1.0, sd 0.25), clipped to 0.45-2.0 | Humans trade irregularly; low values suggest machines |

## 6. How the abuse types are created

Each abuse account starts as a normal-looking account, then one behavior is changed. Half of each type is **obvious** and half is **subtle**.

| Type | Obvious version | Subtle version |
|---|---|---|
| Trial abuse | Age 0-3 days, trades 10-30x its own baseline | Age 0-3 days, trades 3-5x its own baseline |
| Multi-account | 6-12 linked accounts | 3-4 linked accounts |
| Bot | Timing regularity 0.01-0.10 | Timing regularity 0.30-0.44, just below the normal floor of 0.45 |

**Why half are subtle:** if every anomaly were extreme, any method would find them and the results would be circular. Subtle cases sit close to normal behavior so detectors can miss some, which makes the comparison between methods meaningful.

## 7. Known weaknesses of the simulation

- **Subtle multi-account cases do not truly overlap with normal accounts.** Normal accounts have at most 2 linked accounts, so 3-4 is already outside the normal range. Expect detectors to catch these easily; this type is easier than the design suggests.
- **Subtle bots sit just below the hard floor of 0.45** that I set for normal timing. The "edge" is partly an artifact of that clip (about 1% of normal accounts sit exactly at 0.45).
- **Each abuse account changes one behavior only.** Real abusers often combine signals (for example a bot that is also a new account), which this data does not do.
- **Anomalies are drawn from simple uniform ranges.** Real abuse is messier and changes over time.
- **Account-level snapshot.** There is no time dimension, so there is no concept of behavior changing over days or weeks.
- **Fixed 3% prevalence.** Real abuse rates vary and are usually unknown.

## 8. Validation

`validate()` in `src/generate_data.py` runs on every generated dataset and checks: expected columns, no missing values, unique account IDs, numeric types, sensible ranges (for example trades per day above 0, linked accounts between 0 and 12), and that no label column appears in the features. The tests in `tests/test_data.py` check these rules, the row counts, the roughly 3% anomaly rate, and that each abuse type stays within its designed ranges.
